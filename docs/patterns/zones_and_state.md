# Zone & State Patterns

Zone moves, zone-check pitfalls, permanent-instance state (attr_accessors), CardList/Zone filtering. Part of the card-implementation pattern catalog — see `docs/card_patterns.md` for the index.

**Counting lands**: `controller.lands.count` returns the number of land permanents the controller controls (uses `CardList`).

**"Enchant player" (a Curse, or any Aura attaching to a player instead of a permanent)**: `Permanents::Enchantment#attach_to!(target)` (`lib/magic/permanents/enchantment.rb`) already reads generically — `target.attachments << self` — so it works unmodified for a `Player` target as long as `Player` also exposes `.attachments` (a plain `attr_reader`, array, initialized to `[]` in `Player#initialize`, mirroring `Permanent#attachments`). No card-level `resolve!` override needed: just set `def target_choices = game.players` (or a filtered subset) on the card, cast/target it normally, and the base `Attachment#resolve!(target:)` (`super()` then `attach_to!(target)`) does the rest. Read the enchanted player back via `permanent.attached_to` (the same generic reader `attach_to!` already sets) — don't add a separate card-specific accessor for this. Example: `CurseOfThePiercedHeart`.

**`card.creature?` and `card.land?` work on cards in any zone** (not just permanents) — defined in `lib/magic/types.rb` and available on all card objects.

**"Enter the battlefield as a copy of [a creature]"**: `Magic::Permanent#copied_card` is a generic `attr_accessor` on `Permanent` (mirrors the `chosen_creature_type` pattern) that names the `Card` object whose characteristics this permanent should present. `Permanent#copiable_card` (`copied_card || card`) is what everything else reads from: `name`, `cmc`, `mana_value`, `colors`, `colorless?` are defined on `Permanent` as explicit methods delegating to `copiable_card` (rather than `def_delegators :@card`), and `Permanents::ContinuousEffects` (`lib/magic/permanents/continuous_effects.rb`) reads `copiable_card.types` / `.base_power` / `.base_toughness` / `.keywords` / `.activated_abilities` each time it recalculates a permanent's live characteristics — so setting `copied_card` is enough; no explicit refresh call is needed; the next `game.tick!` (which re-runs `apply_continuous_effects!`) picks it up. In the ETB choice's `resolve!(target:)`, just do `actor.copied_card = target.card`. Don't reach for `Permanent#transform!` or `Permanent.resolve(copy: true, ...)` for this — those exist for token copies (`ReflectionOfKikiJiki`, `SublimeEpiphany`) that share the *literal* `Card` object of the thing being copied and rely on `copy: true` to stop `destroy!` from moving that shared card to the graveyard; a non-token copy (e.g. `Clone`) must keep its own `Card` identity so its own zone transitions (death, bounce, exile) stay correct — `copied_card` only overrides how its characteristics are *reported*, it never swaps `@card`. Not yet covered by this mechanism: copying triggered abilities (`etb_triggers`/`death_triggers`/`event_handlers`) or `static_abilities` — only the CDA-style characteristics listed above are live-copied so far. Example: `Clone`.

**Filtering permanents by a subtype like "Aura" (e.g. "target non-Aura permanent")**: `CardList#excluding_type`/`by_any_type` and `Types#type?` do a plain `Array#include?`/`String#include?` check against `permanent.types` — this only works pre-`apply_continuous_effects!`, when a fresh `Card`'s `@types` is still the raw `TYPE_LINE` (a literal string for `Aura`, e.g. `"Enchantment -- Aura"`, so `.include?("Aura")` is a substring check). Once continuous effects run (`ContinuousEffects#calculate_types` does `[*copiable_card.types, ...]`), `permanent.types` becomes an Array containing that whole type-line string as a single element, so `type?("Aura")`/`.include?("Aura")` silently goes from "substring match" to "exact-element match" and returns `false` even for an actual Aura — and continuous effects apply immediately on `Permanent.resolve` (via `Effects::MovePermanentZone`), so this bites on essentially every permanent already on the battlefield, not just after a `game.tick!`. Check the Ruby class instead: `permanent.card.is_a?(Cards::Aura)` (or `Cards::Equipment`, etc. for other CardBuilder base classes) — reliable regardless of continuous-effects timing. Example: `Mirrorform`.

**Moving a card between zones**: Prefer `card.move_to_hand!`/`card.move_to_graveyard!`/`card.move_zone!(to:)` over a manual `from_zone.remove(card); to_zone.add(card)` pair — the manual form skips nothing today (`Zone#add` already sets `card.zone`), but the single-call form is shorter and matches the rest of the codebase. Only reach for manual `remove`/`add` (or `remove`/`push`) when repositioning a card *within the same zone* (e.g. shuffling unchosen cards to the bottom of the library) — there's no "move" happening there. Example: `WrennAndSeven` (+1 ability), `CrownOfSkemfar`.

**`Zone` (`lib/magic/zone.rb`) delegates several `CardList` filters directly** (`.lands`, `.creatures`, `.by_any_type`, `.permanents`, etc.) so `hand.lands` / `graveyard.permanents` work without the `.cards` indirection — prefer that over `hand.cards.lands`. If a `CardList` method you need isn't in `Zone`'s `def_delegators` list yet, add it there rather than routing through `.cards` in card code.

**Don't check `card.zone.battlefield?` to test whether a permanent is on the battlefield**: `Effects::MovePermanentZone#resolve!` sets `target.zone = to` on the *Permanent* only, never on the underlying `Card` — so `permanent.zone.battlefield?` is reliable but `permanent.card.zone.battlefield?` is not. A permanent created via the `ResolvePermanent` spec helper (which calls `Magic::Permanent.resolve(...)` directly, not `Card#resolve!`) leaves `card.zone` `nil` forever, even while the permanent sits on the battlefield — checking it there silently always reads as "not on the battlefield". `Permanent#destroy!`/`#exile!`/`#return_to_hand` are the exception: they explicitly call `card.move_zone!(...)` too, so `card.zone` *is* reliable immediately after those (leaving the battlefield). But `Card#resolve!` (the full cast/play path, not the raw `Permanent.resolve` spec helper) also keeps them in sync on the way in.

**Delirium** ("if there are four or more card types among cards in your graveyard"): No shared delirium/threshold helper exists yet — check it inline in the triggered ability's `should_perform?`/a private method: `controller.graveyard.cards.flat_map { |card| TYPE_PREDICATES.select { |p| card.public_send(p) } }.uniq.size >= 4`, with `TYPE_PREDICATES = %i[creature? artifact? enchantment? instant? sorcery? land? planeswalker?]` as a card-local constant — these are the plain `Types` predicates (`lib/magic/types.rb`), already reliable on graveyard cards since delirium only ever inspects cards off the battlefield (no continuous-effects timing pitfall like the Aura substring-matching note above). Example: `GibberingFiend` (delirium gates an "at the beginning of each opponent's upkeep, deal 1 damage" trigger — combine with `opponent?` from the base `TriggeredAbility`, not `TriggeredAbility::BeginningOfYourUpkeep`, since the trigger needs to fire on the *opponent's* upkeep, not the controller's).

**"Target opponent gains control of this creature"** (control-change effect): No dedicated control-change mechanic existed — `Permanent#controller` already has a plain `attr_accessor`-style setter (`controller=`), and the battlefield is one shared `Zone` (not per-player), so changing control is just `source.controller = target` inside the ability's `resolve!` — no zone move, no `Effects::*` class needed. `Permanent#owner` stays unchanged (death still sends the card to the *owner's* graveyard via `owner.hand`/`owner.graveyard`, matching real rules), so only `controller` should be reassigned. Order matters when combined with another effect in the same `resolve!` (e.g. "Draw two cards. Target opponent gains control of this creature."): trigger the other effect *before* reassigning `controller`, since effects like `Effects::DrawCards` default their acting player off `source.controller` at the moment `trigger_effect` is called. For "activate only during your turn", override `requirements_met?` to check `game.current_turn.active_player == controller` (queried by `Actions::ActivateAbility#can_be_activated?`, per the Static/Triggered pattern in `CelestialEnforcer`). Example: `HumbleDefector`.

**`Permanent#exiled_cards` is already a general-purpose "cards exiled with this permanent" list** (`attr_reader`, initialized to an empty `Magic::CardList` in `Permanent#initialize`, already used by `AgathasSoulCauldron`, `AnnexSentry`, `GraspOfFate`, `IdolOfEndurance`, `SerpentsSoulJar`, `EvendoBrushrazer`) — for "exile a card... [track it as] exiled with this [permanent]" wording, just push onto `actor.exiled_cards`/`source.exiled_cards` directly. Don't redefine `exiled_cards` as a card-local method in a class reopening: `actor`/`source` inside triggers and abilities is always the `Permanent`, not the `Card`, so a same-named method on the card class is simply never reached (dead code, easy to miss since nothing errors — the real `Permanent#exiled_cards` silently answers instead). Example: `ArcaneBombardment`.

**Card-instance-specific persistent state on a permanent that isn't yet covered by an existing accessor** (e.g. "count how many times this permanent's mana ability has been activated, pending being spent on X"): follow the existing `chosen_creature_type`/`exile_cast_permission_turn`/`ring_bearer`/`prevent_opponent_lifegain_turn` precedent — add a plain `attr_accessor` directly on `Magic::Permanent` (`lib/magic/permanent.rb`), with any non-nil default initialized in `Permanent#initialize` (e.g. `@pending_mana_ability_uses = 0`), even when only one card currently needs it. Same reason as `exiled_cards` above: a same-named method defined only in the card's own class reopening is invisible from ability/trigger code, since `actor`/`source` there is always the `Permanent`, not the `Card`. Example: `PyromancersGoggles` — since the engine has no per-mana-source tagging (see the "restricted-use mana" note above), "when *that* mana is spent to cast a red instant or sorcery" is approximated as a per-activation counter (`pending_mana_ability_uses`, incremented by the mana ability's `resolve!`, decremented and consumed by the first qualifying `SpellCast` after) rather than tracking the literal mana; matches this codebase's established looseness around unenforced mana-restriction cards (`PlazaOfHeroes`) — just approximated from the opposite side (consumption instead of production).

**State-based actions (rule 704)**: Live in `Magic::Game::StateBasedActions` (`lib/magic/game/state_based_actions.rb`) — one private method per rule, `perform!` runs one pass and returns whether anything changed. `Game#check_state_based_actions!` loops passes until stable, then checks state-triggered abilities; `Game#tick!` is an alias, so existing specs that call `game.tick!` still work. The engine calls `Game#state_based_actions_checkpoint!` (same thing, but a no-op while `stack.pending_choices?`) after every `Turn#take_action`, after each item `Stack#resolve_stack!` resolves, and after `Stack#resolve_choice!` — so **specs and cards should not call `game.tick!` to make a creature die**; it happens on its own after a cast/resolve. The "pending choices" guard matters: a card that models a replacement effect as a multi-step choice (`Clone`'s "may copy" then "pick target") would otherwise be a 0/0 and die between the two steps. Things that change state *without* going through an action/resolution/choice (a bare `permanent.destroy!`, `take_damage`, `change_loyalty!`, `attach_to!` in a spec) need an explicit `game.check_state_based_actions!` before asserting on the result. Gotchas: (1) Aura/Equipment cards declare `TYPE_LINE` as one string (`"Enchantment -- Aura"`), so `permanent.type?("Aura")` is false — the SBA checks `card.is_a?(Cards::Aura)` too; (2) `Permanent#activated_abilities` are rebuilt on every continuous-effects pass, so compare ability objects by class and `source`, never identity, across an SBA check; (3) queuing a `Choice` (the legend rule's `Choice::LegendRule`) does not count as a "change", and the rule skips permanents already covered by a pending legend-rule choice, so repeated checks don't stack duplicates; (4) `destroy!` is the raw "move to graveyard" primitive and does *not* consult `indestructible?` — only the lethal-damage/deathtouch SBA does, so a "destroy target creature" effect that should respect indestructible (`Effects::DestroyTarget` currently does not) is still to do. Not covered yet: Aura enchant restrictions (only "host gone" is checked), and simultaneous losses leaving the game drawn.
